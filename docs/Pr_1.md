## 📚 Основные идеи и теоретические основы

Разработчики приложений редко работают в одиночку. В крупных проектах в области веб-/облачных/мобильных приложений, в проектах искусственного интеллекта обычно задействовано множество людей — разработчики интерфейса, серверной части, баз данных и многие другие.
Вносимые каждым участником изменения обязательно должны отслеживаться и контролироваться руководителем, чтобы исключить значимые ошибки в условиях совместной работы.
Для организации такой работы применяются технологии распределённого контроля версий.

### История Git

Разработка Linux в начале 2000-х годов осуществлялась в рамках бесплатной системы, известной как BitKeeper.
В 2005 году BitKeeper превратился в платную систему, что создало определённые проблемы для разработчиков Linux.
Линус Торвальдс возглавил команду по разработке новой системы контроля версий исходного кода.
Проект реализовывался в короткие сроки, а его ключевые характеристики были определены в следующем виде:

- поддержка нелинейного развития (в то время патчи для Linux приходили со скоростью 6,7 патчей в секунду, необходимо было обеспечить эффективное решение связанных с данной особенностью задач);
- распределённая разработка: каждый разработчик должен иметь локальную копию полной истории разработки;
- совместимость с существующими системами и протоколами, что необходимо для обеспечения разнообразия сообщества Linux;
- эффективное управление крупными проектами;
- аутентификация истории: это гарантирует, что все распределённые системы будут иметь идентичные обновления кода;
- подключаемые стратегии слияния: множество путей развития приводят к сложным интеграционным решениям, которые могут потребовать чётких интеграционных стратегий.

Распределённые системы контроля версий (Distributed Version Control Systems, DVCS) стали важнейшими инструментами для совместной разработки ПО.
Их используют не только инженеры-программисты и специалисты DevOps, но и многие другие специалисты, в том числе в области Data Science.
Они полезны везде, где требуется отслеживание изменений/версий и/или сотрудничество между несколькими пользователями.

Несмотря на то, что существует множество распределённых систем управления версиями, Git является одной из самых популярных.
Популярность Git делает его важным навыком для специалистов, связанных с разработкой ПО.

### Что такое Git?

Система контроля версий позволяет отслеживать изменения в ваших документах. Это позволяет восстановить старые версии документа, если была допущена ошибка, и значительно упрощает сотрудничество с другими разработчиками.

Git — бесплатное программное обеспечение с открытым исходным кодом, распространяемое по лицензии GNU General Public License.
Git — это распределённая система контроля версий, т.е. пользователи в любой точке мира могут получить копию вашего проекта на своём компьютере.
После того как они внесли изменения, они могут синхронизировать свою версию с удалённым сервером, чтобы поделиться ею с вами.

Git — не единственная существующая система контроля версий, но данная технология фактически обеспечивает аспект распределённой работы, что и стало основной причиной её значительной популярности.

### GitLab

GitLab — это полноценная платформа DevOps, представленная в виде одного приложения. GitLab предоставляет доступ к репозиториям Git, контролируемую системой управления исходным кодом.
С GitLab разработчики могут:

- Просматривать код, оставляя комментарии и помогая улучшать код друг друга.
- Работать со своей локальной копией кода.
- Осуществлять ветвления и слияния при необходимости.
- Оптимизировать тестирование и доставку с помощью встроенной непрерывной интеграции (CI) и непрерывной доставки (CD).

Другие платформы: GitHub, BitBucket, GitLab.

### Основные термины

- *Протокол SSH* — метод безопасного удалённого входа с одного компьютера на другой.
- *Репозиторий* — место, которое содержит папки вашего проекта, для которых настроен контроль версий.
- *Форк / fork* — копия репозитория.
- *Merge request (MR)* — способ запроса на то, чтобы кто-то рассмотрел и утвердил предложенные вами изменения.
- *Working directory* — рабочая директория, содержит файлы и подкаталоги на вашем компьютере, которые связаны с Git-репозиторием.

### Основные команды Git

Когда вы начинаете работу с новым репозиторием, его создание происходит только один раз: либо локально с последующей отправкой на сервер, либо путём клонирования существующего репозитория.

- *git add* — перемещает изменения из рабочего каталога в промежуточную область (staging area).
- *git status* — позволяет видеть состояние вашего рабочего каталога и промежуточный снимок ваших изменений.
- *git commit* — делает снимок изменений и фиксирует их в проекте.
- *git reset* — отменяет изменения, внесённые вами в файлы в вашем рабочем каталоге.
- *git log* — позволяет просматривать предыдущие изменения в проекте.
- *git branch* — позволяет создать изолированную среду в вашем репозитории для внесения изменений.
- *git checkout* — позволяет просматривать и изменять существующие изолированные среды (ветки).
- *git merge* — позволяет соединить ветки воедино.

### Ветвление (Branch)

Все файлы в Git хранятся в отдельных ветках (branches).
Разработчики работают над исходными файлами в ветках. Основная ветка (main) хранит развертываемую версию вашего кода.
Она создаётся по умолчанию, однако вы можете использовать любую ветку в качестве основной.

Когда вы планируете что-то изменить, вы создаёте новую ветку и даёте ей понятное имя.
Новая ветка создаётся как точная копия исходной.
Когда вы вносите изменения, созданная вами ветка сохраняет изменения.

### Коммит (Commit)

Чтобы изменить содержимое файла в Git, необходимо не просто внести изменения, но и выполнить *commit* — фиксацию.
Commit означает, что разработчик убеждён, что код представляет собой стабильную основу для разрабатываемой функции.

Когда разработчик фиксирует изменённый исходный код, он должен написать комментарий, описывающий изменения.
Комментарий должен быть содержательным. Некоторые дополнительные «правила приличия»:

- Не заканчивайте сообщение при коммите точкой.
- Сообщения о коммитах должны содержать не более 50 символов — для подробной информации используйте расширенное описание.

### Merge Request

Разработчики могут изменять исходные файлы в ветке, но изменения не будут опубликованы до утверждения. Порядок работы:

1. Подается команда *pull* (или создаётся merge request).
2. Код рассматривается и утверждается.
3. Утверждённый код объединяется с основным кодом.

Когда все изменения в ветке завершены, эта ветка считается устаревшей и её следует удалить.

### Fork и Clone

Системы контроля версий с распределённым исходным кодом позволяют нескольким разработчикам проектов параллельно работать над его кодовой базой.

**Clone** — создание локальной копии удалённого репозитория:

```bash
git clone git@gitlab.example.com:user/repo.git
```

Каждый разработчик может иметь на своём компьютере собственную копию репозитория.
Копия на компьютере разработчика — это *local repo*.
Копия на GitLab-сервере — это *remote repo*.

**Fork** — создание полной копии репозитория на GitLab-сервере:

Перейдите на страницу проекта → нажмите **Fork** → выберите проект-родитель.
Проект, из которого вы создаёте ответвление, называется *upstream*.

GitLab предоставляет следующие возможности:

### 📁 Создание репозитория в GitLab

1. В GitLab нажмите **New project** → **Create blank project**
2. Заполните данные:
   - **Project name** — имя репозитория (например: `my_first_repo`)
   - **Project description** — описание (необязательно)
   - **Visibility** — выберите **Private** (для учебных репозиториев)
   - Поставьте галочку **Initialize repository with a README**
3. Нажмите **Create project**

Вы будете перенаправлены в созданный репозиторий. Корневая папка содержит файл `README.md`.

**Редактирование файла README**

1. Нажмите на иконку карандаша (Edit)
2. Измените текст
3. Прокрутите вниз до раздела **Commit changes**
4. Добавьте сообщение о фиксации (commit message)
5. Нажмите **Commit changes**

**Создание нового файла**

1. Нажмите **Add file** → **New file**
2. Введите имя файла (например: `firstpython.py`)
3. Добавьте содержимое
4. Прокрутите вниз, добавьте описание и нажмите **Commit changes**

**Загрузка файла из локальной системы**

1. Нажмите **Add file** → **Upload file**
2. Выберите файл
3. Нажмите **Commit changes**

### 📁 Создание ветки (Branch)

1. Перейдите на главную страницу вашего репозитория
2. В верхней части списка файлов найдите раскрывающееся меню **main** (основная ветка)
3. Нажмите на него, введите имя новой ветки (например: `feature-branch`) и нажмите Enter

В вашем репозитории теперь две ветки: `main` и `feature-branch`.
Все файлы из основной ветки скопированы в новую.

**Создание файла в новой ветке:**

1. Убедитесь, что выбрана ваша ветка (`feature-branch`)
2. Нажмите **Add file** → **New file**
3. Введите имя файла (например: `testbranch.py`)
4. Добавьте содержимое
5. Нажмите **Commit new file**

Файл в дочерней ветке не добавляется автоматически в основную.

**Сравнение веток и создание Merge Request:**

1. В вашей ветке нажмите **Compare & merge request**
2. GitLab покажет изменения между `main` и `feature-branch`
3. Добавьте комментарий (необязательно)
4. Нажмите **Merge branch into main**

### 📁 Операция слияния (Merge)

1. Откройте вкладку **Merge requests** — список ожидающих запросов
2. Выберите merge request, который хотите объединить
3. Если изменения вас устраивают, нажмите **Merge**
4. Нажмите **Confirm merge** для завершения

После слияния можно удалить дочернюю ветку.

### 📁 Работа с локальным репозиторием через командную строку

Возвращаемся в окно Terminal JupyterLab.

**Создание локального репозитория:**

```bash
mkdir myrepo
cd myrepo
git init
ls -la .git
```

**Создание и добавление файлов:**

```bash
touch newfile.txt
git add newfile.txt
```

**Настройка пользователя Git:**

```bash
git config --global user.email "student_pia_01@academic"
git config --global user.name "Иванов Иван"
```

**Фиксация изменений:**

```bash
git commit -m "added newfile.txt"
```

**Создание и переключение ветки:**

```bash
git branch my1stbranch
git branch
git checkout my1stbranch
```

> 💡 Можно создать ветку и сразу перейти в неё одной командой:
> ```bash
> git checkout -b my1stbranch
> ```

**Внесение изменений:**

```bash
echo 'Here is some text in my newfile.' >> newfile.txt
cat newfile.txt
touch readme.md
git add readme.md
```

**Проверка статуса:**

```bash
git status
```

Команда показывает, какие файлы готовы к фиксации.
Для добавления всех изменений:

```bash
git add *
git status
```

**Фиксация и просмотр истории:**

```bash
git commit -m "added readme.md modified newfile.txt"
git log
```

> 💡 Для выхода из `git log` нажмите `q`.

**Откат изменений:**

```bash
git revert HEAD --no-edit
```

**Добавление ещё одного файла:**

```bash
touch goodfile
git add goodfile
git commit -m "added goodfile"
git log
```

**Слияние ветки с основной:**

```bash
git checkout main
git merge my1stbranch
git log
```

**Удаление объединённой ветки:**

```bash
git branch -d my1stbranch
```

### 📁 Работа с удалённым репозиторием

**Подключение удалённого репозитория:**

```bash
git remote add origin git@gitlab.<server-ip>:<username>/myrepo.git
```

**Отправка изменений на сервер:**

```bash
git push -u origin main
```

> ⚠️ Для работы по SSH убедитесь, что ваш SSH-ключ добавлен в GitLab (см. Практическую работу №0).

**Получение обновлений:**

```bash
git pull origin main
```

**Проверка удалённых репозиториев:**

```bash
git remote -v
```

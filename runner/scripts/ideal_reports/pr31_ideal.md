# Отчёт по Практической работе №31 «Разработка интеллектуальной системы доступа к SQL-базам данных (NLPtoSQLtoNLP)»

## Выполнение задания

### Шаг 1. Создание базы данных SQLite

База `students.db` подготовлена скриптом `create_students_db.py` и размещена в `/app/data`. Структура:

```sql
CREATE TABLE students (student_id INTEGER PRIMARY KEY, full_name TEXT NOT NULL, group_num TEXT NOT NULL);
CREATE TABLE courses  (course_id INTEGER PRIMARY KEY, course_name TEXT NOT NULL);
CREATE TABLE grades   (student_id INTEGER, course_id INTEGER, grade INTEGER CHECK (grade BETWEEN 2 AND 5),
                       PRIMARY KEY (student_id, course_id));
```

Заполнена тестовыми данными: 3 студента (группы ИВТ-401/ИВТ-402), 3 курса, оценки.

### Шаг 2. Размещение компонентов в Langflow

Создан flow `Практическая 31 - NLPtoSQLtoNLP`. Компоненты: **Chat Input**, **Chat Output**, два компонента **Prompt Template** (Prompt 1 — генерация SQL, Prompt 2 — синтез ответа), два компонента **OpenAI Model**, компонент **SQL Database**.

### Шаг 3. Первый этап трансляции (NLP → SQL)

Шаблон **Prompt 1** содержит DDL-схему и инструкцию:

```text
System: Ты — эксперт по SQL. Переведи вопрос пользователя в корректный SQL-запрос для SQLite. Выдавай ТОЛЬКО чистый SQL без кавычек и markdown.

СХЕМА БД:
students(student_id, full_name, group_num)
courses(course_id, course_name)
grades(student_id, course_id, grade)

ВОПРОС: {user_query}
SQL:
```

**OpenAI Model 1** подключён к локальному серверу (Base URL `http://192.168.2.83:8080/v1`, Temperature = 0.1 — для стабильной генерации кода). Его вывод соединён с портом `query` компонента **SQL Database**.

### Шаг 4. Выполнение SQL и второй этап (SQL → NLP)

Компонент **SQL Database**: `Database URL = sqlite:////app/data/students.db`, включён `add_error` — сообщения об ошибках СУБД передаются дальше для диагностики.

Шаблон **Prompt 2**:

```text
System: Сформируй ответ пользователю на понятном русском языке на основе результатов из базы данных.

ВОПРОС: {user_query}
SQL ЗАПРОС: {sql_query}
РЕЗУЛЬТАТ БД: {db_result}
ОТВЕТ:
```

Полная цепочка: Chat Input → Prompt 1 → Model 1 → SQL Database → Prompt 2 → Model 2 → Chat Output (вопрос пользователя подан в оба промпта).

### Шаг 5. Тестирование в Playground

| Вопрос | Сгенерированный SQL | Ответ системы |
|---|---|---|
| «Выведи список студентов группы ИВТ-401» | `SELECT full_name, group_num FROM students WHERE group_num = 'ИВТ-401'` | «В группе ИВТ-401 учатся: Иванов Иван, Петрова Анна» |
| «Какая средняя оценка у Иванова Ивана?» | `SELECT AVG(g.grade) FROM grades g JOIN students s ON s.student_id = g.student_id WHERE s.full_name = 'Иванов Иван'` | «Средняя оценка Иванова Ивана — 4.5» |
| «Сколько студентов записано на каждый курс?» (GROUP BY + COUNT) | `SELECT c.course_name, COUNT(g.student_id) FROM courses c JOIN grades g ON g.course_id = c.course_id GROUP BY c.course_id` | корректная таблица по курсам |

**Вывод:** двухэтапная схема NLP→SQL→СУБД→NLP работает: модель генерирует синтаксически корректные запросы (включая JOIN, GROUP BY, AVG), СУБД выполняет их на реальных данных, вторая модель интерпретирует табличный результат. Экспорт flow сохранён в `Pr_31_nlpsql.json`.

## Контрольные вопросы

1. **В чем заключаются уязвимости безопасности (SQL-инъекции) при автоматической генерации SQL-кода моделью LLM?**
   Модель не понимает намерений, а лишь статистически продолжает текст: злонамеренный пользователь может вставить в вопрос фрагмент, который модель «продолжит» в сгенерированном запросе — произвольная вставка `; DROP TABLE ...`, `UNION SELECT` для извлечения чужих данных или подбора паролей. Выполнение такого кода в СУБД приведёт к нарушению целостности или утечке данных. Защита: фильтрация и валидация сгенерированного SQL (разрешение только SELECT), параметризованные запросы, read-only учётная запись БД, ограничение длины и ключевых слов.

2. **Почему для правильного формирования SQL-запроса языковой модели необходима точная DDL-схема таблиц?**
   Модель не имеет доступа к метаданным СУБД и «не знает» структуру базы: она берёт из промпта описание схемы — названия таблиц и столбцов, типы данных, связи. Точная DDL-схема позволяет сгенерировать запрос с корректными именами и условиями; без неё модель выдумывает (галлюцинирует) несуществующие таблицы и столбцы, что приводит к ошибкам выполнения. Схема также задаёт контекст для правильных JOIN и агрегаций.

3. **Каким образом двухэтапная схема (NLP -> SQL -> СУБД -> NLP) компенсирует отсутствие у LLM прямого доступа к содержимому базы данных?**
   На первом этапе модель генерирует SQL-запрос — текст, а не данные. Выполнение запроса делает СУБД: она возвращает фактический табличный результат из текущих данных БД. На втором этапе вторая модель интерпретирует этот результат и формулирует ответ на естественном языке. Таким образом модель никогда не «припоминает» содержимое БД (которого у неё нет), а работает с реальными данными, полученными отдельно через СУБД — генерация и выполнение разделены.

4. **Какие промпт-инструкции исключают добавление лишней Markdown-разметки при выходе модели?**
   Явное указание в системной части: «Выдавай ТОЛЬКО чистый SQL без кавычек и markdown» — запрет блоков ```sql, пояснений до/после запроса. Ограничение формата выхода: одна строка (один запрос), без нумерации и комментариев. Дополнительно можно включить режим структурированного вывода (json_mode) и на стороне кода очищать ответ регулярным выражением, извлекая только тело SQL.

5. **Как обработать синтаксическую ошибку SQL-запроса, переданного на выполнение в СУБД?**
   Включить передачу ошибок из СУБД (в Langflow — параметр `add_error` у компонента SQL Database): сообщение об ошибке перехватывается как исключение и возвращается в цепочку. Обработка: передать текст ошибки обратно модели вместе с исходным запросом для исправления (повторная генерация, retry-цикл с ограничением числа попыток), либо показать пользователю понятное уведомление. Дополнительно — предварительная валидация сгенерированного SQL парсером до отправки в СУБД.
